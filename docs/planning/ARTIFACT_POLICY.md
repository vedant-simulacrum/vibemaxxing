# Artifact and Evidence Policy

## Purpose

Prevent generated outputs, environment-specific probes, placeholders, and release evidence from being confused with authoritative specifications or production proof.

## Classes

### Authoritative source

ADRs, specifications, schemas, state machines, planning tasks, threat models, and policies. These are reviewed and versioned in Git.

### Deterministic fixture

Small synthetic inputs and expected outputs used by tests. Fixtures must contain no private user data and must document their generator or provenance.

### Reproducible generated artifact

Benchmark, conformance, or evaluation output generated by a committed command. Commit only when needed for review or baseline comparison. Include tool version, source commit, environment, timestamp, and command.

### Environment probe

Machine-specific capability output. It is never product evidence by itself. Commit only sanitized synthetic or intentionally public examples; otherwise keep local or attach to a private run.

### Release evidence

Checksums, SBOM, provenance, signatures, TUF metadata, consumer verification, migration, and recovery evidence tied to an immutable release commit. Do not create before the release workflow exists.

### Placeholder

README scaffolds, empty directories, declared cases, and `not_applicable` evals. Placeholders must never be described as implemented or passing.

## Required metadata

Generated evidence must record:

- schema version;
- source commit;
- producing command and tool versions;
- platform and relevant resource profile;
- fixture or dataset identifier;
- privacy classification;
- result status;
- known limitations.

## Commit rules

- Never commit prompts, transcripts, code from private repositories, paths, credentials, environment values, or personal data.
- Prefer synthetic fixtures.
- Large or transient outputs belong in CI artifacts or release storage, not Git.
- Committed generated artifacts must be reproducible and reviewed.
- Any artifact referenced as proof must link to its owning task, eval, and acceptance gate.
- `artifacts/` may contain seed examples today; their status must remain explicit.

## Regeneration

`FILE_INDEX.md`, `MANIFEST_FILES.txt`, and `SHA256SUMS` are generated package metadata. Regenerate them after repository structure changes; do not hand-edit their contents without also documenting the generator.

## Deletion

Remove stale generated outputs when their schema, source commit, or owning test is obsolete. Preserve immutable release evidence according to the release and retention policies.
