# VibeProof v1 conformance corpora

Status: normative planning fixtures; no implementation consumes them yet
Normative owners: `docs/architecture/VIBEPROOF_V1_PROTOCOL.md`, `packages/schemas/vibeproof-claim-v1.cddl`
Updated: 2026-08-09

This directory holds the fixtures that pin VibeProof v1's wire behaviour. Everything
here is `normative-planning` under `docs/planning/ARTIFACT_POLICY.md` with an evidence
ceiling of `fixture-consistent`. A fixture states what an implementation must do. It
is not evidence that one does, and no VibeProof implementation reads any file in this
directory today.

| File | Owns |
| --- | --- |
| `exact-byte-vectors.json` | canonical CBOR, the COSE_Sign1 profile, and exact signed bytes for one claim and one receipt |
| `malformed-resource-corpus.json` | decoder rejection and resource-limit cases, and the sole *byte-level* negative corpus |
| `ed25519-divergence-corpus.json` | the Ed25519 verification criterion, where RFC 8032 leaves two answers open |
| `zip215-oracle-run.json` | what three real verifiers answered for the divergence corpus, with provenance |
| `zip215-oracle/` | the Go program that produced those answers |
| `fork-and-rotation-vectors.json` | what a decoder must conclude when one lineage presents two continuations, and what a device-key transition must carry to be authorized |

`exact-byte-vectors.json` is regenerated by `scripts/repository/generate_vibeproof_vectors.py`.
The divergence corpus is regenerated by `scripts/repository/generate_ed25519_divergence_corpus.py`.
Neither file is hand-edited; both generators have a `--check` mode that fails when the
committed file differs from a regeneration, so an edited verdict fails rather than persists.

## The fork and rotation vectors

`fork-and-rotation-vectors.json` is the third corpus in this directory, and it is
allowed to be here for the reason the second negative corpus was not: it declares no
CDDL rule. Its subject is what a conforming decoder must *conclude* from fields the
grammar already owns — `vibeproof-claim-v1`'s lineage identifier, sequence and
commitment heads, and the rotation transition's two signatures — rather than how any
of them is encoded. `validate_vibeproof_rule_ownership` refuses a rule name in any JSON
document under `conformance/` or `evals/` outside the two vector files, and it passes
over this one because there is nothing in it to refuse.

Its normative authority is `docs/architecture/VIBEPROOF_V1_PROTOCOL.md` sections
"Claim and checkpoint continuity" and "Rotation, recovery and gaps", with
`docs/security/INTEGRITY_MODEL.md` owning the fork resolution the protocol section
points at. The suite's two declared authorities are unchanged; a fork is a decision
taken over VibeProof fields under VibeProof's own continuity section, not a second wire
format.

`validate_lineage_fork_and_rotation` in
`scripts/repository/validate_planning_artifacts.py` replays it. Every disposition is
recomputed rather than read, so a vector cannot record an outcome the stated rules do
not produce; each forked lineage is assembled into a
`packages/schemas/fork-resolution-v1.schema.json` record and validated against it, so
the corpus cannot describe a resolution the normative record has no shape for; and each
check constraint on `device_key_events` is asserted present verbatim, so the rule in
Python and the rule in PostgreSQL cannot come apart.

Two of the five lineages exist to stop the corpus rewarding a resolver that quarantines
everything — a control that accepts four submissions in a row, and one whose two
malformed submissions are *refused* rather than quarantined, because neither identifies
a branch. A fork corpus without them is passed by refusing all input.

The three authorizations of an ordinary rotation are each removed in turn, and each
removal must be refused. The protocol contract names three separate things — a payload
"signed independently by both old and new keys" and a server that "verifies recent
authentication" — while `device_key_events` recorded one nullable `continuity_signature`
and no account authorization at all, so an ordinary rotation and a single-signature
forgery were the same row until `PF-010`.

## Which file owns which CDDL rule

`packages/schemas/vibeproof-claim-v1.cddl` declares twenty-six rules. Each is owned by
exactly one of the two vector files, declared in that file rather than inferred, and
`validate_vibeproof_rule_ownership` in `scripts/repository/validate_planning_artifacts.py`
fails when the three sets do not partition the grammar exactly.

| Owner | Rules | What the claim means |
| --- | --- | --- |
| `exact-byte-vectors.json` `cddl_rules_pinned` | 16 | The reference closure of the six messages the vectors encode. The validator recomputes that closure from the grammar and requires the declared list to equal it, so the list cannot be padded or left behind |
| `malformed-resource-corpus.json` `cddl_rules_pinned` | 6 | `batch-context`, `gap-declaration`, `key-rotation-transition-v1`, `dual-authorized-rotation-v1`, `cose-sign1-rotation-v1`, `correction-record-v1`. Each is named by at least one negative case and every case's rule is one of these |
| `malformed-resource-corpus.json` `cddl_rules_unpinned` | 4 | `verifier-appraisal-v1`, `challenge-v1`, `atomic-batch-result-v1`, `claim-result-v1`. No vector encodes them; each entry carries a reason and the work unit that will |

Pinning by the exact-byte vectors is verified rather than asserted. Both payloads and
both protected-header maps are decoded and checked against their rules: the label set
must match exactly in both directions, because the grammar's preamble closes its maps,
and every value must satisfy its declared type. The COSE_Sign1 envelopes are checked
structurally as tag 18 over four elements holding the fixture's own protected bytes,
an empty unprotected bucket, the payload and a 64-byte signature.

Before this the repository compared no committed byte to the grammar.
`validate_cddl_file` proves the CDDL parses and that named rules exist, and says so in
its own docstring; the vectors could have encoded a different message entirely, signed
it correctly, reproduced from the recorded seed, and passed every check.

A third file may not declare a rule. `PF-054` originally planned a second negative
corpus at `negative-vectors.json` in this directory; it is not written, because a rule
declared there would be a second authority for the same wire format, and because
`validate_conformance_manifests` fails on any file here that no manifest case names.

## The negative corpus decodes

Nine of the twenty-seven cases state their input as hex and name a `decoder_signal`.
`validate_vibeproof_negative_corpus` decodes each one with the canonical profile
decoder and requires it to be refused with exactly that signal — not merely to fail.
A case that named a malformation its bytes did not contain used to pass; it now does
not. Every refusal the profile decoder can produce is covered by at least one case,
so a rule the profile enforces cannot go missing from the corpus silently.

The remaining eighteen state a mutation, a generator or a transaction state in prose.
They are not executable and are not counted as though they were.

## The divergence corpus

### What it proves

That the Ed25519 verification criterion is a real choice with real consequences, and
that VibeProof v1 has made it.

RFC 8032 §5.1.7 says checking the cofactored group equation `[8][S]B = [8]R + [8][k]A`
is "sufficient, but not required", which permits the cofactorless `[S]B = R + [k]A`
instead. §8.8 concedes that implementations then "disagree about the exact set of valid
signatures". FIPS 186-5 §7.7 reproduces the same permission verbatim, so citing FIPS
resolves nothing either. A cofactored verifier accepts a strictly larger set than a
cofactorless one and the implication runs one way only, so a Rust signer and a Go
verifier that both conform to RFC 8032 can disagree about whether a signature is valid.
D-192 resolves this by pinning VibeProof v1 to **ZIP-215**: non-canonical `A` and `R`
encodings are accepted, `S` must be strictly less than `ℓ`, and the cofactored equation
must hold.

The corpus is nine cases. Four cover the axes `PF-068` requires — non-canonical `A`,
non-canonical `R`, small-order `A`, and `S ≥ ℓ` — and the rest exist to keep those four
from being misread:

| Case | Axis | ZIP-215 | Strict RFC 8032 |
| --- | --- | --- | --- |
| `control-canonical-valid` | control | accept | accept |
| `non-canonical-a-identity` | non-canonical `A` | accept | reject |
| `non-canonical-a-mixed-order` | non-canonical `A` | reject | reject |
| `non-canonical-r-identity` | non-canonical `R` | accept | reject |
| `non-canonical-r-order4` | non-canonical `R` | accept | reject |
| `small-order-a-order8` | small-order `A` | accept | reject |
| `cofactored-only-order8-r` | cofactor alone | accept | reject |
| `s-equals-l` | `S ≥ ℓ` | reject | reject |
| `s-plus-l` | `S ≥ ℓ` | reject | reject |

Five separate the two criteria. `cofactored-only-order8-r` is the one to read first:
every byte in it is canonically encoded, `A` is an ordinary public key with a full-order
point, and the two criteria still disagree. The divergence is not a story about malformed
encodings. It is the group equation.

`non-canonical-a-mixed-order` is the counterweight. ZIP-215 accepts the non-canonical
*encoding* and then rejects the *signature*, because accepting a point is not accepting
a signature over it. A verifier that implements "non-canonical encodings are accepted"
by deleting the check passes `non-canonical-a-identity` and fails here.

`s-equals-l` and `s-plus-l` record where ZIP-215 is not more permissive. It requires
`S < ℓ` exactly as RFC 8032 §5.1.7 does, and an implementer who reads ZIP-215 as
uniformly laxer drops the one range check that stops signature malleability.

### Why RFC 8032's own test vectors are insufficient

They are well-formed signatures. Every conforming implementation accepts them, under
either group equation, which is exactly why they cannot detect which equation is in
use. `tests/ci/test_ed25519_divergence_corpus.py` asserts this rather than claiming it:
it runs RFC 8032 §7.1 TEST 1 through both verification rules in the generator and
requires both to accept. A conformance suite built from RFC 8032's vectors reports green
against a cofactored verifier and a cofactorless one alike, and a cross-language suite
built from them reports agreement between two implementations that will disagree in
production on the first adversarial input. Only adversarial inputs separate the criteria
sets, and that is the only thing this corpus contains.

### How each verdict was confirmed

The generator computes its own ZIP-215 verdicts from its own curve arithmetic. That is
the weakest evidence a corpus can carry: if the generator misreads ZIP-215 and the
comment beside it misreads ZIP-215 the same way, they agree and neither is right.
Asserting a verdict from specification text is the same defect as citing RFC 8032 and
calling verification pinned, one level up.

So every verdict is confirmed against an implementation that is not this generator.
`conformance/vibeproof/v1/zip215-oracle/` verifies each case with
**`github.com/hdevalence/ed25519consensus` v0.2.0** — the ZIP-215 implementation Zcash
and CometBFT use, written by a co-author of the ZIP — and records the answer against a
SHA-256 digest of that case's exact id, public key, `R`, `S` and message. The generator
consumes that record. A case whose digest the record covers is emitted `confirmed`; a
case it does not cover is emitted `unconfirmed` and carries the command that would
confirm it; and a case where the oracle contradicts the computed verdict stops the
generator from writing the corpus at all.

**All nine ZIP-215 verdicts are currently `confirmed` by `ed25519consensus` v0.2.0.**
The record pins the module version and its `go.sum` `h1:` digest, so a confirmation
cannot silently move to a different implementation.

Refresh it with:

```
python3 scripts/repository/run_ed25519_oracles.py          # needs Go and the module proxy
python3 scripts/repository/generate_ed25519_divergence_corpus.py
python3 scripts/repository/generate_ed25519_divergence_corpus.py --check
```

The order matters and converges in one pass: a case's digest depends only on its bytes,
so the oracle can be run against a corpus whose confirmations are not yet filled in.

One limitation, stated rather than left to be discovered. CI does not re-run the oracle:
`scripts/ci/verify_repository.py` builds `apps/api` and no other Go module, so the
confirmation is a committed record made on a named toolchain rather than a check that
executes on every push. What CI does enforce is that the corpus still reproduces from
its recorded inputs, that every `confirmed` case resolves against a matching digest in
the run record, and that the recorded verdicts still match the rules the generator
implements — so a corpus edited away from its confirmations fails, and only a
confirmation that was never refreshed can go stale. `run_ed25519_oracles.py --check`
re-runs all three verifiers and fails if any verdict moved.

### The contrast column, and what it is not

Go's `crypto/ed25519` and Python's `cryptography` (over OpenSSL) are also run over every
case. Both are cofactorless. Neither is ZIP-215, and **neither verdict is ever recorded
as a ZIP-215 verdict** — `test_the_contrast_oracles_are_never_recorded_as_zip215` fails
if one is. They are there because the classic answer is half of every case, and because
the difference between the columns is the whole point of the corpus.

Running them turned up something worth recording. The corpus carries two different
divergence fields, because collapsing them into one boolean would state a falsehood:

* `against_strict_rfc8032` — five cases, measured against a strict reading of RFC 8032
  §5.1.3 and §5.1.7 implemented in the generator;
* `against_observed_cofactorless` — **four** cases, naming the implementations that
  actually returned the other answer when run.

The case in the gap is `non-canonical-a-identity`. RFC 8032 §5.1.3 says decoding fails
when the recovered `y` is at least `p`, so the strict rule rejects it. Go's
`crypto/ed25519` and OpenSSL both **accept** it. Two widely deployed verifiers accept a
public-key encoding the specification says must fail to decode, which means "cofactorless"
is not one behaviour either, and it is a second reason the corpus records what
implementations *did* rather than what a specification says they should have done.

### What it does not prove

* Nothing about any implementation. No Rust or Go verifier reads this corpus; `P-003`
  and `P-004` are the units that make one do so, and `P-003`'s acceptance criterion is
  that every case here yields its recorded verdict.
* Not cross-language parity. That needs two independent implementations running the
  corpus and agreeing, and two implementations agreeing on the wrong authority is not
  conformance in any case.
* Nothing about security, privacy, or launch readiness.
* Not that `ed25519consensus` is the Go verifier VibeProof will ship. Selecting one is
  part of the D-012 bakeoff. It is used here as an oracle, and an oracle is a measuring
  instrument rather than a dependency of the product.

### Scope

The corpus tests raw Ed25519 signature verification. Its message is a fixed ASCII string
rather than a COSE `Sig_structure`, so a failure localises to the verification rule and
not to an encoder; the COSE_Sign1 and canonical-CBOR bindings are owned by
`exact-byte-vectors.json`. Both corpora describe the same test-only signer seed, which is
published in both files and is never a key that signs anything real.

The small-order points and the non-canonical encodings are derived at generation time —
the 8-torsion by multiplying a low-`y` curve point by `ℓ` and enumerating the result's
multiples, the non-canonical set by exhausting the nineteen residues that have a second
encoding — and both derivations are recorded in the corpus under `derived_facts`. No
constant in this corpus is pasted from a source whose derivation it cannot show.
